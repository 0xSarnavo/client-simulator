              - heading "Automated accessibility testing and its limitations" [level=2] [ref=e888]
              - generic [ref=e889]:
                - link "edit":
                  - /url: /w/index.php?title=Web_accessibility&action=edit&section=31
            - paragraph [ref=e890]: Automated accessibility testing tools have become a widely used first step in identifying accessibility barriers on websites. Tools such as axe-core, WAVE, and Lighthouse evaluate a web page's Document Object Model (DOM) against rule sets derived from the Web Content Accessibility Guidelines (WCAG) and related standards, flagging violations such as missing alternative text, insufficient colour contrast, or absent form labels.
            - paragraph [ref=e891]:
              - text: However, automated tools are capable of detecting only a portion of the accessibility issues present on a given page. Analysis of axe-core — the engine underlying tools such as Google Lighthouse — found that automated rules could be applied to approximately 16 out of 50 WCAG 2.1 Level AA success criteria, supporting industry estimates of 20–30% coverage when measured by criteria count.
              - superscript [ref=e892]:
                - link "[87]" [ref=e893] [cursor=pointer]:
                  - /url: "#cite_note-87"
              - text: When measured by volume of real-world issues rather than criteria count, the same analysis found automated testing identified approximately 57% of issues found during full audits, as certain failure types occur with disproportionate frequency.
              - superscript [ref=e894]:
                - link "[88]" [ref=e895] [cursor=pointer]:
                  - /url: "#cite_note-88"
              - text: Academic research evaluating multiple tools against identical content found that even running six automated tools in parallel left half of all WCAG 2 success criteria uncovered, with an estimated six in ten violations missed.
              - superscript [ref=e896]:
                - link "[89]" [ref=e897] [cursor=pointer]:
                  - /url: "#cite_note-89"
              - text: A further independent analysis concluded that approximately 42% of WCAG success criteria cannot be detected through automated scanning at all, as they require human judgement about the quality, appropriateness, or usability of content.
              - superscript [ref=e898]:
                - link "[90]" [ref=e899] [cursor=pointer]:
                  - /url: "#cite_note-90"
            - paragraph [ref=e900]:
              - text: The W3C Web Accessibility Initiative states that "tools cannot check all accessibility aspects automatically" and that human judgement is required, noting that evaluation tools can sometimes produce false or misleading results.

            - region [ref=e903]:
              - generic [ref=e904]:
                - heading "Limitations of static DOM analysis" [level=3] [ref=e905]
                - generic [ref=e906]:
                  - link "edit":
                    - /url: /w/index.php?title=Web_accessibility&action=edit&section=32
              - paragraph [ref=e907]: Most automated tools operate by inspecting the static structure of a web page — its HTML, ARIA attributes, and computed styles — without interacting with the page as a user would. This approach has inherent limitations in several areas.
              - paragraph [ref=e908]:
                - text: Presence versus function. A tool can confirm that a skip navigation link exists in the DOM, but cannot verify that activating it correctly moves keyboard focus to the main content area. Automated scans can reliably detect the presence of skip links or landmark regions, but verification that they function correctly requires behavioural testing.
                - superscript [ref=e909]:
                  - link "[92]" [ref=e910] [cursor=pointer]:
                    - /url: "#cite_note-92"
              - paragraph [ref=e911]:
                - text: Accessible name quality. Tools can confirm that an interactive element has an accessible name, but cannot assess whether that name is meaningful or useful in context. A button labelled "click here" or an image with alt text reading "photo" satisfies the relevant automated rule while providing no useful information to a screen reader user. Distinguishing a name that exists from a name that communicates intent requires contextual judgement that deterministic rules cannot supply.
                - superscript [ref=e912]:
                  - link "[93]" [ref=e913] [cursor=pointer]:
                    - /url: "#cite_note-93"
              - paragraph [ref=e914]: Dynamic content. Web applications frequently modify the DOM in response to user interaction. Modals, disclosure widgets, carousels, and single-page application routing can all introduce accessibility barriers that are absent from the initial page load and therefore invisible to a static scan.
              - paragraph [ref=e915]:
                - text: Keyboard and focus behaviour.
                - link "WCAG" [ref=e916] [cursor=pointer]:
                  - /url: https://en.wikipedia.org/wiki/Web_Content_Accessibility_Guidelines
                - text: Success Criterion 2.1.1 (Keyboard) requires that all functionality be operable via keyboard. Verifying this requires simulating keyboard navigation — tabbing through interactive elements, triggering actions, and confirming that focus is managed correctly. Accessible modal dialogs are additionally required to confine focus within the dialog while open and return focus to the triggering element on close; detecting incorrect focus management requires operating the modal, not inspecting its markup.

                - link "Playwright" [ref=e922] [cursor=pointer]:
